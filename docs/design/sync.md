# 다중 모니터 동기화 설계

> 이 문서는 4가지 재생 모드 중 **순환 동기화(synchronized-cycle)** 의 시간 계산을 상세히 설명한다. 개별·동시·통합 모드, 모니터 수·배치·이미지 수 처리, 관리/엔진/송출 분리는 `docs/design/architecture.md`를 따른다.

## 1. 목표

- 인포메이션센터 4대의 모니터가 같은 시각에 다음 이미지로 넘어간다.
- 예: 1주기 A·B·C·D, 2주기 D·A·B·C처럼 모니터별로 다른 이미지를 보여주면서 전체 순서는 함께 움직인다.
- 모니터별로 재생목록을 다르게 할 수 있어야 한다.
- 서버가 잠시 끊겨도 마지막 콘텐츠를 계속 재생하고, 복구 후 자동으로 다시 맞춘다.
- 재부팅·브라우저 재시작 후에도 현재 위치로 즉시 복귀한다.

## 2. 핵심 아이디어

이미지 전환 신호를 매번 네트워크로 보내지 않는다. 서버가 **공통 시간축(epoch)** 과 **재생목록**을 배포하고, 각 플레이어가 서버와 맞춘 시계로 현재 위치를 스스로 계산한다.

```text
현재 위치(ms) = (서버와 맞춘 현재 시각 - epoch) mod 전체 재생시간
현재 이미지   = 현재 위치가 속한 구간의 이미지
화면별 이미지 = (기본 순서 + 화면 오프셋 + 회전 방향 × 주기) mod 이미지 수
```

이 방식의 장점:

- 화면이 늦게 켜지거나 재부팅해도 즉시 현재 위치로 복귀한다.
- 네트워크가 끊겨도 각자 계산을 계속하므로 전체가 멈추지 않는다.
- 전환 메시지를 놓쳐서 특정 화면만 뒤처지는 문제가 없다.
- 화면 수가 늘어도 서버 부하가 거의 늘지 않는다.

## 3. 서버가 배포하는 값

```json
{
  "version": 17,
  "centerId": "info-a",
  "epoch": "2026-11-24T09:00:00+09:00",
  "items": [
    { "id": "a", "url": "/media/a.jpg", "durationMs": 10000 },
    { "id": "b", "url": "/media/b.jpg", "durationMs": 10000 },
    { "id": "c", "url": "/media/c.jpg", "durationMs": 10000 },
    { "id": "d", "url": "/media/d.jpg", "durationMs": 10000 }
  ],
  "displays": [
    { "id": "m1", "startIndex": 0, "step": -1 },
    { "id": "m2", "startIndex": 1, "step": -1 },
    { "id": "m3", "startIndex": 2, "step": -1 },
    { "id": "m4", "startIndex": 3, "step": -1 }
  ]
}
```

- `epoch`: 모든 화면이 공유하는 기준 시각. 재생목록을 게시할 때 새로 정한다.
- `items[].durationMs`: 이미지별 표시 시간. 합계가 전체 주기다.
- `startIndex`: 첫 주기에 그 화면이 보여줄 이미지 위치.
- `step`: 주기가 바뀔 때 이미지가 이동하는 방향. `-1`이면 A·B·C·D → D·A·B·C.
- 화면별로 다른 재생목록을 쓰려면 `displays[]`에 `playlistId`를 두고, 화면별 `items`를 참조하게 한다. 동기화 계산은 같은 epoch·전체 주기를 공유한다.

### 이미지 수와 모니터 수가 다를 때

- 계산식은 이미지 수 `N`과 모니터 수 `M`을 상수로 두지 않는다.
- `N=0`이면 플레이스홀더, `N=1`이면 유지, `1<N<M`이면 라운드로빈·반복, `N>M`이면 시간에 따라 전체 이미지를 순환한다.
- 관리 화면에서 `LCM(N, M)` 주기까지 패턴을 미리 보여주고, 중복·빈 슬롯을 경고한다. 상세 규칙은 `architecture.md` 6절에 있다.

### 다른 모드와의 관계

- **개별 재생**: 각 화면이 자기 재생목록·시간축을 쓴다. 이 문서의 공통 epoch 계산을 쓰지 않아도 된다.
- **동시 재생(mirror)**: 모든 화면의 `startIndex`와 `step`을 같게 두면 이 문서의 계산식이 그대로 동시 재생이 된다.
- **통합 화면(canvas)**: 한 이미지를 가상 캔버스에 놓고 화면별로 자른다. 시간축은 공유하지만 이미지 선택이 아니라 `sourceRect` 계산이 핵심이다.

## 4. 시계 맞추기

브라우저의 `Date.now()`는 PC 시계에 의존하므로 PC마다 오차가 있을 수 있다. 서버와의 왕복 시간을 측정해 오프셋을 보정한다.

1. `/api/time`에 8회 요청한다.
2. 각 요청의 `t0`(보내기 전), `t1`(받은 뒤), `serverTime`을 기록한다.
3. 왕복 시간(`t1 - t0`)이 가장 작은 표본을 고른다.
4. `offset = serverTime - (t0 + t1) / 2`로 서버 시계와의 차이를 계산한다.
5. 30초마다 다시 맞춘다. 화면이 다시 보이거나 네트워크가 복구될 때도 즉시 다시 맞춘다.
6. 오프셋은 `localStorage`에 저장하고, 서버가 끊기면 마지막 값을 사용한다.

`performance.now()`(단조 시계)를 함께 사용해 사용자가 PC 시계를 바꿔도 재생 위치가 튀지 않게 한다.

## 5. 전환 시점

- 다음 경계까지 남은 시간을 계산해 `setTimeout`으로 예약한다.
- 경계 직전에 한 번 더 `requestAnimationFrame`으로 확인해 브라우저 타이머 지연을 보정한다.
- 이미지 전환은 300ms 페이드로 한다. 100~200ms 정도의 미세한 차이는 페이드가 시각적으로 가린다.
- 백그라운드 탭은 브라우저가 타이머를 늦추므로, 화면마다 **별도 창**을 띄우고 절전·화면 끄기를 해제한다.

## 6. 늦은 접속·재부팅·서버 단절

| 상황 | 동작 |
|---|---|
| 화면이 늦게 켜짐 | 서버 시계를 맞추고 현재 위치를 계산해 즉시 해당 이미지 표시 |
| 브라우저 재시작 | 저장된 manifest와 epoch로 현재 위치 계산, 서버가 있으면 새 manifest 확인 |
| 서버 단절 | 마지막 manifest·epoch·오프셋으로 계속 재생, 화면에 작은 오프라인 표시 |
| 서버 복구 | manifest 버전을 확인하고 새 재생목록이 있으면 다음 경계에서 반영 |
| 재생목록 게시 | epoch를 새로 정해 모든 화면이 같은 시점에 새 주기 시작 |
| PC 시계 변경 | `performance.now()` 기반으로 재생 위치를 유지 |
| 네트워크 지터 | 최소 왕복 표본을 사용하고, 유선 LAN을 권장 |

## 7. 한 PC에 모니터 여러 대 vs 모니터마다 PC

### 한 PC에 여러 모니터

- 한 프로세스가 모니터마다 테두리 없는 창을 하나씩 띄운다.
- 한 타이머로 모든 창을 전환하므로 네트워크 시계 동기화가 필요 없다. 가장 안정적이다.
- 구현은 Windows WPF(.NET Framework 4.8) 또는 Electron 중에서 고른다. 이미지 중심이면 WPF가 가볍고, 웹 콘텐츠·동영상이 많으면 Electron/Chromium이 낫다.
- 각 창은 `Screen.AllScreens`의 위치·크기를 사용해 배치한다.

### 모니터마다 PC

- 각 PC의 브라우저가 같은 서버에 접속하고, 화면 ID별로 위치를 계산한다.
- 서버는 시간과 manifest만 제공하고, 각 플레이어가 독립적으로 재생한다.
- 유선 LAN과 NTP를 권장한다.

### 혼합

- 한 센터는 한 PC + 여러 창, 다른 센터는 PC별 브라우저로 구성해도 된다. 서버의 manifest 형식은 같다.

## 8. 시뮬레이션 결과

2026-11-24에 4개 화면, 이미지 1장당 10초, A·B·C·D → D·A·B·C 조건으로 두 가지 방식을 비교했다.

### 단순 1회 동기화

- 화면별 시계 오차 -30~+80ms, 네트워크 지터 ±20~110ms, 렌더 지연 15~45ms를 가정.
- 최대 전환 오차 **235ms**, 평균 68ms, 95백분위 235ms.
- 200ms 목표를 넘었다. 지터가 큰 환경에서는 한 번 맞추는 방식으로는 부족하다.

### 최소 왕복 8회 표본

| 네트워크 가정(편도 지연) | 최대 오차 | 95백분위 | 150ms 이내 |
|---|---:|---:|---|
| 좋은 유선 LAN (1~10ms) | 43ms | 39ms | 예 |
| 보통 유선 LAN (1~30ms) | 53ms | 41ms | 예 |
| 나쁜 유선 LAN (1~100ms) | 81ms | 54ms | 예 |
| 나쁜 Wi-Fi (1~300ms) | 173ms | 107ms | 아니오 |

- 늦은 접속 시 위치 불일치: 0건.
- 10분 서버 단절: 50ppm 시계 드리프트와 렌더 지연을 포함해 최대 155ms.
- 결론: **유선 LAN + 최소 왕복 시계 보정**이면 이미지 전환에 충분한 수준(±100ms 안팎)을 기대할 수 있다. Wi-Fi가 불안정하면 페이드 시간을 늘리거나 유선을 설치해야 한다.

이 수치는 알고리즘 검증용 시뮬레이션이며, 실제 브라우저 렌더링·타이머·PC 성능은 PoC에서 다시 측정한다.

## 9. PoC에서 확인할 것

- 4개 브라우저 창에서 A·B·C·D → D·A·B·C가 같은 시각에 바뀌는가?
- 1시간 동안 최대 전환 오차가 200ms 이내인가?
- 화면을 늦게 열어도 즉시 올바른 위치로 들어오는가?
- 서버를 10분 끊어도 계속 재생되고, 복구 후 다시 맞는가?
- 브라우저를 재부팅해도 자동 복귀하는가?
- 4K 이미지 20장을 미리 로드해도 메모리·전환이 버티는가?
- 세로 모니터에서 이미지가 잘리지 않는가?

## 10. 한계와 대비

- 브라우저 타이머는 백그라운드 탭에서 느려진다. 키오스크 창을 별도로 띄우고 절전을 끈다.
- 영상은 이미지보다 동기화가 어렵다. 영상이 필요하면 리드 디스플레이 방식(Xibo)이나 영상 전용 플레이어를 검토한다.
- PC 시계가 크게 틀어져도 `performance.now()`와 서버 오프셋으로 보정하지만, 초기 접속 시 서버에 닿아야 한다.
- 서버가 오래 끊기면 PC의 단조 시계 드리프트가 누적된다. 10분 단위는 문제없지만, 장시간 단절 뒤에는 복구 시 재동기화가 필요하다.
- 보안상 관리 화면은 원내망에만 열고, 업로드 파일 형식·크기를 제한하며, 기본 비밀번호를 반드시 바꾼다.
