# 권고안: 국립부산국악원 인포메이션센터 디지털 사이니지

작성 2026-11-24 / 1차 조사·검증 결과 / 같은 날 범용·UI·UX 요구 반영

## 결론

**모니터 수·배치·해상도·방향을 설정으로 다루는 범용 이미지 송출 엔진을 경량 자체 개발하는 것을 1순위로 권고한다.** 관리 프로그램, 순수 재생 엔진, 송출 모듈을 분리하고, 1대~다수 모니터, 이미지 0~N장, 개별·순환·동시·통합 모드를 같은 엔진으로 처리한다.

단, 다음 경우에는 결론이 달라진다.

1. **기존 프로그램이 USB 파일 시스템·코덱·해상도 문제로 간단히 고쳐지면** 새로 만들지 말고 수리를 먼저 끝낸다. 진단 비용이 개발 비용보다 훨씬 싸다.
2. **기존 PC가 Windows 10/11이고 Docker를 돌릴 Linux 서버·VM이 있으면** Xibo CE를 1개 화면 파일럿으로 먼저 검증한다. 기능 성숙도와 한글 CMS는 Xibo가 가장 앞서 있다. 다만 Docker·AGPL·CMS 운영 부담이 있다.
3. **최신 UI·UX와 빠른 도입이 우선이고 단일 개발자 유지보수 위험을 감수할 수 있으면** ScreenTinker를 1~2개 화면 파일럿으로 검증한다.

한 문장으로 정리하면 다음과 같다.

> “고칠 수 있는 고장은 먼저 고치고, Windows 10/11 + Docker가 보장되면 Xibo를 파일럿하며, 범용 배치·한글 UI·기존 장비 활용이 핵심이면 모듈형 경량 엔진을 만든다.”

## 0. 2026-11-24 추가 요구 반영

이번 추가 요구로 범위가 “2개 센터의 4대 모니터”에서 “장소마다 1대~다수 모니터를 설정하는 범용 시스템”으로 넓어졌다.

- 모니터 수·배치·해상도·방향을 코드에 고정하지 않는다.
- 장소별 독립 모니터 그룹, 가로·세로·격자·사용자 지정 배치.
- 연결된 모니터 자동 인식과 수동 등록.
- 이미지 규격 검사·비율 유지, 이미지 수와 모니터 수가 달라도 동작.
- 개별·순환·동시·통합 화면 재생.
- 모니터 추가·연결 해제 대응, 실제 송출 전 가상 모니터 미리보기.
- 장비 지원 기능에 따른 송출 모듈 선택.
- 관리 프로그램·재생 엔진·송출 모듈 분리.
- 국내외 실제 서비스 화면·매뉴얼·데모 벤치마킹과 KRDS 기반 UI·UX, 작동형 프로토타입.

이 요구는 4대 고정 PoC로는 충족할 수 없다. 구현 기준은 `docs/design/architecture.md`, 화면 기준은 `docs/design/ui-ux.md`, 일정·공수는 `docs/plan.md`를 따른다. 전체 일정은 **14~20주**, 공수는 **약 60~90 person-days**로 다시 잡았다.

## 1. 왜 이 결론인가

이번 요구의 핵심은 거대한 CMS가 아니다. 범용 배치와 초보자 사용성이다.

- 장소별 1대~다수 모니터, 독립 그룹
- 가로·세로·격자·사용자 지정 배치
- 이미지 0~N장, 모니터 수와 무관한 재생
- 개별·순환·동시·통합 화면
- 모니터 자동 인식·수동 등록·추가/해제
- 이미지 규격 검사·비율 유지·가상 미리보기
- 같은 시각에 다음 이미지로 전환
- 이미지 순서·표시 시간 설정
- 재부팅 후 자동 복구
- 서버가 끊겨도 마지막 콘텐츠 유지
- 일반 직원이 매뉴얼 없이 쓰는 한글 관리 화면
- 추가 구매·구독 0원

Xibo는 이 요구를 제품 기능으로 거의 다 덮지만, PHP·MySQL·Docker CMS와 Windows 10+ 플레이어를 전제로 한다. Anthias는 미러 전용이고, Concerto는 동기화가 없으며, ScreenTinker는 MIT로 매력적이지만 단일 개발자 유지보수와 Windows 비디오월 미검증이라는 위험이 있다. 경량 자체 개발은 기능 범위를 좁히는 대신 기존 장비·한글 UI·정확한 회전 규칙을 맞출 수 있다.

## 2. 네 가지 접근 비교

| 접근 | 이번 요구 적합도 | 장점 | 단점 | 판단 |
|---|---|---|---|---|
| 기존 프로그램 정상화 | 조건부 높음 | 가장 싸고 빠름. 사용법이 이미 익숙 | 원인 미확인. 노후 프로그램이면 재발 가능 | **먼저 진단** |
| 오픈소스 도입(Xibo) | 높음(조건부) | 성숙한 동기화·스케줄·권한·한글 CMS | Docker 서버, Windows 10+, AGPL 검토, 운영 부담 | **Windows 10/11 + Docker가 되면 파일럿** |
| 오픈소스 개조 | 낮음 | 기존 제품에 기능을 얹을 수 있음 | 업스트림 충돌, 유지보수 부담, 보안 검토 | **권장하지 않음** |
| 경량 자체 개발 | 매우 높음 | 기존 장비·한글·정확한 회전·무도커 | 개발·테스트·인수인계 필요 | **1순위** |

### 오픈소스 개조를 권장하지 않는 이유

- Anthias에 화면별 오프셋을 넣으려면 재생 엔진과 배포 구조를 건드려야 한다. 미러 전용 설계와 충돌한다.
- Concerto에 동기화를 넣으려면 3.0 RC 코드와 프런트엔드 재생 로직을 수정해야 한다. 안정판 2.3.6은 2017년 것이다.
- ScreenTinker는 이미 비디오월 기능이 있으므로 개조보다 설정·파일럿이 먼저다. 다만 단일 개발자 프로젝트를 기관이 장기 운영하려면 지원·포크 전략이 필요하다.
- Xibo는 이미 동기화가 있으므로 개조할 이유가 없다. 도입 여부만 판단하면 된다.

## 3. 권장 구조(경량 자체 개발)

이 절은 2개 센터 예시다. 모니터 수·배치를 고정하지 않는 전체 구조와 데이터 모델은 `docs/design/architecture.md`를 따른다.

```text
[관리자 PC] ── 브라우저 ──> [원내 서버: Node.js + SQLite]
                                  │  manifest, 이미지, 시각 API
                                  ├── [A센터 플레이어 1] ─ 모니터 1
                                  ├── [A센터 플레이어 2] ─ 모니터 2
                                  ├── [B센터 플레이어 1] ─ 모니터 3
                                  └── [B센터 플레이어 2] ─ 모니터 4
```

### 서버

- Node.js 20/22 LTS + SQLite. Docker 없이 Windows 또는 Linux에서 실행한다.
- 이미지 파일은 로컬 볼륨에 두고, 정적 파일로 제공한다.
- API: 재생목록 조회, 서버 시각, 화면 등록, 상태 보고, 관리자 업로드·편집.
- 관리 화면: 센터 선택, 이미지 업로드, 순서·표시 시간, 화면별 시작 위치·회전 방향, 가로/세로 미리보기, 게시·되돌리기.
- 인증: 원내 계정 또는 로컬 관리자 계정. 최소 권한, 세션 만료, 업로드 확장자·크기 검증.

### 플레이어

- HTML/CSS/JavaScript 웹 앱. Edge/Chrome 키오스크 모드에서 전체 화면으로 실행한다.
- 목표 브라우저: Chrome/Edge 109 이상(Windows 7/8.1에서 마지막으로 쓸 수 있는 계열). 최신 문법을 과도하게 쓰지 않는다.
- Service Worker로 이미지와 manifest를 캐시한다. 서버가 끊겨도 마지막 재생목록으로 계속한다.
- 화면 ID별 `startIndex`, `step`으로 A·B·C·D → D·A·B·C를 만든다.
- 디버그 오버레이(화면 ID, 현재 이미지, 다음 전환까지 남은 시간, 시계 오차)를 숨김 키로 연다.

### 한 PC에 모니터 여러 대

- WPF(.NET Framework 4.8) 또는 Electron으로 모니터마다 테두리 없는 창을 하나씩 띄운다.
- 한 타이머로 모든 창을 바꾸므로 네트워크 동기화가 필요 없다. 가장 안정적이다.
- 이미지 중심이면 WPF가 가볍고, 웹 콘텐츠·동영상이 많으면 Electron/Chromium이 낫다.
- Windows 7까지 고려하면 .NET Framework 4.8 WPF가 브라우저보다 예측 가능하다. 단, 동영상 코덱은 별도 검증이 필요하다.

### 모니터마다 PC

- 각 PC의 브라우저가 같은 서버에 접속하고, 화면 ID별로 위치를 계산한다.
- 유선 LAN과 NTP를 권장한다. Wi-Fi가 불안정하면 페이드 시간을 늘리거나 유선을 설치한다.

### 운영

- Windows 작업 스케줄러로 로그인 시 자동 실행, 브라우저가 죽으면 다시 띄우는 watchdog.
- 자동 로그인, 절전·화면 끄기 해제, Windows 업데이트 재부팅 정책 확인.
- 서버 DB·이미지·설정을 매일 백업하고, 복구 절차를 문서화한다.
- 장애 시 마지막 화면을 유지하고, 관리 화면에 오프라인 상태를 표시한다.

## 5. 다중 모니터 동기화 기술 검증

자세한 내용은 `docs/design/sync.md`에 있다. 요약하면 다음과 같다.

- 서버가 공통 epoch와 재생목록을 배포하고, 각 화면이 `(현재 시각 - epoch) mod 전체 주기`로 현재 이미지를 계산한다.
- 화면별 시작 위치와 회전 방향을 두어 A·B·C·D → D·A·B·C를 만든다.
- 시계는 `/api/time` 8회 샘플 중 최소 왕복 지연을 골라 보정한다.
- 시뮬레이션 결과: 단순 1회 동기화는 최대 235ms까지 벌어졌고, 최소 왕복 8회 방식은 좋은 유선 LAN 43ms, 보통 53ms, 나쁜 유선 81ms였다. 나쁜 Wi-Fi는 173ms로 150ms 목표를 넘었다.
- 늦은 접속 불일치 0건, 10분 서버 단절 최대 155ms.
- 결론: 유선 LAN + 최소 왕복 시계 보정이면 이미지 전환에 충분하다. 실제 브라우저 PoC로 재검증한다.

## 6. 추가 확인이 필요한 장비 정보

우선순위가 높은 것부터 확인한다. 전체 목록은 `docs/research/equipment-checklist.md`에 있다.

1. 모니터 제조사·모델·수량·해상도·설치 방향·입력 단자
2. 모니터마다 PC가 있는지, 한 PC에 여러 모니터가 연결되는지
3. PC 운영체제와 빌드(Windows 7/10/11), CPU·RAM·그래픽 출력
4. 현재 송출 프로그램 이름·버전·설치 경로·오류 메시지
5. USB 파일 시스템·폴더 구조·파일명·이미지 형식·해상도
6. 유선 LAN·Wi-Fi·IP 방식·방화벽·프록시·NTP
7. Docker/WSL2·무설치 실행파일·원격 접속 허용 여부
8. 관리자 권한·백신·보안성 검토 절차
9. 콘텐츠 담당자·교체 주기·승인 절차·운영 시간
10. 재부팅·정전·절전·자동 로그인 설정

이 중 1~3번만 확인되어도 “경량 자체 개발 vs Xibo”의 큰 방향을 정할 수 있다. 4~5번은 기존 프로그램 수리 가능성을 판단한다.

## 7. 예상 개발 규모와 비용

내부 인력 1명 기준의 거친 추정이다. 실제 일정은 장비 확인과 보안 검토에 따라 달라진다.

| 단계 | 예상 공수 | 내용 |
|---|---:|---|
| 조사·현장 진단 | 4~6일 | 후보·UI·UX 벤치마킹, 장비·프로그램·네트워크 조사 |
| UI·UX 설계·프로토타입 | 10~14일 | IA, 화면 설계, 작동형 프로토타입, 사용성 테스트 |
| 범용 엔진 PoC | 14~18일 | 동적 모니터·배치·4개 모드·미리보기·동기화 |
| MVP 통합 | 20~28일 | 관리 화면, 서버, 웹 플레이어, 등록, 오프라인, 자동 시작 |
| A센터 현장 시범·안정화 | 10~14일 | 설치, 2주 무인 운전, 재부팅·단절·교체 시험 |
| B센터·교육·인수인계 | 4~6일 | 확대, 교육, 운영 문서 |
| 합계 | **약 60~90일** | 1인 기준 약 14~20주 |

- 소프트웨어 구매비·구독료: **0원**. 오픈소스 런타임과 자체 코드만 사용한다.
- 추가 장비: 기존 PC·모니터·네트워크로 해결하는 것을 우선한다. 유선 LAN 공사, UPS, 소형 서버가 필요하면 별도 견적이 든다.
- 네이티브 다중 창 플레이어를 MVP에 포함하면 10~15일이 더 든다. 웹 플레이어만으로 먼저 시작할 수 있다.
- 외주 개발 시: 위 공수에 업체 단가를 곱해야 하므로 이 문서에서는 금액을 단정하지 않는다. 내부 개발이 어려우면 60~90일 범위를 기준으로 견적을 비교한다.
- Xibo 대안: 파일럿·설치·교육 5~10일. 라이선스 0원이지만 Docker 서버·VM과 AGPL 검토가 필요하다.
- 기존 프로그램 수리: 진단 0.5~2일. 수리 범위에 따라 별도.

## 8. 단계별 계획

### 0단계: 조사·현장 진단 (1~2주)

- 국내외 실제 화면·매뉴얼·데모·KRDS 조사
- 후보별 범용 배치·동기화·한글·초보자 UX 비교
- 장비·기존 프로그램·USB·네트워크·보안 조건 조사
- **결정:** 수리 / 경량 개발 / Xibo·ScreenTinker 파일럿

### 1단계: UI·UX 설계·프로토타입 (2~3주)

- IA, 6단계 첫 사용 흐름, 화면 설계
- 작동형 프로토타입, 담당 직원 사용성 테스트
- **결정:** 화면 구조·용어·기능 범위 확정

### 2단계: 범용 엔진 PoC (3~4주)

- 동적 모니터·배치·이미지 수/모니터 수·4개 모드
- 가상 미리보기, 자동/수동 등록, 시간 동기화
- **결정:** 웹 플레이어만 / 네이티브 다중 창 포함

### 3단계: MVP 통합 (4~6주)

- 프로토타입 UI + 서버·엔진·플레이어
- 인증·권한·백업·자동 시작·오프라인
- **결정:** A센터 현장 시범 승인

### 4단계: A센터 현장 시범·안정화 (2~3주)

- 실제 설치, 2주 무인 운전, 재부팅·단절·교체 시험
- 직원 교육·피드백 반영
- **결정:** B센터 확대 / 보완

### 5단계: B센터·인수인계 (2주)

- B센터 설치, 센터별 독립 콘텐츠 확인
- 운영 문서·교육·유지보수 체계
- **최종:** 직원이 외부 도움 없이 운영

상세 일정·산출물·통과 기준은 `docs/plan.md`를 따른다.

## 9. 위험과 대비

| 위험 | 영향 | 대비 |
|---|---|---|
| 장비 정보가 늦어짐 | 설계 확정 지연 | 진단 스크립트와 체크리스트로 먼저 수집. PoC는 장비와 무관하게 진행 |
| Windows 7/8.1·구형 브라우저 | 최신 웹 기능 사용 불가 | Chrome/Edge 109 타깃, 필요하면 WPF 대안 |
| 네트워크 지터·Wi-Fi | 화면 간 전환 오차 | 유선 LAN, 최소 왕복 시계 보정, 300ms 페이드 |
| 서버 PC 고장 | 전체 화면 멈춤 | 플레이어 오프라인 캐시, 서버 백업, watchdog, 예비 PC |
| 보안성 검토 | 무설치·비서명·Docker 반려 | 원내망 전용, 인증, 업로드 검증, 최소 권한, 서명·반입 절차 사전 협의 |
| 유지보수 인력 부재 | 장기 운영 위험 | 작은 코드베이스, 테스트, 문서, Xibo 대안 유지 |
| AGPL(Xibo) | 수정·배포 시 소스 공개 의무 | 법무·보안 검토, 수정 없이 사용, 필요하면 상용 라이선스 |
| 콘텐츠 품질 | 글자 잘림·해상도 저하 | 가로/세로 템플릿, 안전 영역, 미리보기, 자동 리사이즈 |

## 10. owner 결정이 필요한 것

1. **0단계 현장 진단을 먼저 승인**할지
2. 진단 결과를 본 뒤 **경량 개발 / Xibo 파일럿** 중 하나를 고를지
3. 현장 시범 일정과 담당 직원을 지정할지
4. 저장소를 원내 private로 둘지, 나중에 공개할지
5. 자체 코드 라이선스를 MIT/Apache-2.0 중 무엇으로 할지(공개 시)
