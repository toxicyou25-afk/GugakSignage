# Generic image signage PoC

This directory is a small, runnable technical proof for the National Busan Gugak Center signage project. It verifies the pure playback engine, a minimal HTTP server, a browser player, and a virtual-monitor preview without fixing monitor counts, image counts, layouts, or modes in the UI.

The PoC is deliberately not a production release. It has no authentication, upload UI, video support, or appliance packaging. Every demo image is original vector artwork generated by [`tools/generate-media.mjs`](tools/generate-media.mjs); no third-party screenshots or proprietary assets are included. Source, generated media, and documentation in `poc/` are Apache-2.0; see [License and provenance](#license-and-provenance).

## Run it

Requirements: Node.js 20 or newer. Node 24.22.2 was used for verification. The server uses only Node built-ins and needs no Docker, database, package install, or cloud service.

```powershell
cd poc
npm start -- --port 4174
```

`4174` is used in the examples because port `4173` was occupied by an unrelated process on the verification machine. The default port is `4173` if it is free.

Reset the demo state and start again:

```powershell
npm start -- --port 4174 --reset
```

The server prints preview and player URLs and stores minimal state in `apps/server/data/state.json` (ignored by git). All example URLs below assume `http://127.0.0.1:4174`.

## Engine

The engine is ESM with no DOM, filesystem, network, or timer access. It is imported unchanged by Node tests, the server, the player, and the preview. Public entry points are in [`packages/engine/index.js`](packages/engine/index.js).

### Data and layouts

Runtime validation covers `Site`, `DisplayGroup`, `Display`, `Layout`, `Playlist`, `ImageAsset`, and `Publication`. Layout slots use normalized `x/y/w/h` coordinates; `canvasWidth/canvasHeight` are metadata for aspect and real pixel mapping. Displays are mapped by stable display ID and optional `slotId`, never by array position. Single, row, column, grid, and custom layouts all produce the same slot vocabulary.

Each display carries its own resolution, orientation, rotation, fit preference, and optional synchronized offsets. A display resolution is the content viewport; rotation is applied by the output renderer. The engine warns when orientation and resolution disagree.

### Modes

| Mode | Selection rule |
|---|---|
| `individual` | Each display advances through its own playlist timeline from `startOffsetMs`/`startIndex`; item durations are honored. |
| `synchronized-cycle` | Shared epoch and dwell. Display `i` shows `(startIndex_i + step_i × slot) mod N`. |
| `mirror` | Shared epoch/dwell and one image for every display, ignoring per-display offsets. |
| `canvas` | Shared epoch/dwell and one image across the wall; each display gets a source crop from its layout slot. |

Synchronized modes use one group dwell. If playlist item durations differ, the engine emits `SYNC_DURATION_OVERRIDE`; per-item durations still apply to individual mode.

### Image count N and monitor count M

The engine handles all cases without branching the player on a fixed monitor count:

- `N=0`: placeholder RenderPlan, `NO_IMAGES` warning, no next change.
- `N=1`: static image on every display, `SINGLE_IMAGE` info.
- `N<M`: repeated images, distributed by offset and flagged.
- `N=M`: one-to-one at slot zero.
- `N>M`: the visible image window rotates, so all images are used over time.
- `patternPreview()` returns up to `LCM(N,M)` slots (capped and marked truncated if necessary).

### RenderPlan

`buildRenderPlan(snapshot, displayId, atMs)` returns an output-module-neutral plan:

```json
{
  "displayId": "disp-a3",
  "at": "2026-11-24T09:00:05.000Z",
  "imageId": "asset-welcome",
  "imageIndex": 0,
  "imageCount": 3,
  "sourceRect": { "x": 0, "y": 0, "w": 1920, "h": 1080 },
  "destinationRect": { "x": 0, "y": 656.25, "w": 1080, "h": 607.5 },
  "viewport": { "width": 1080, "height": 1920 },
  "rotation": 0,
  "fit": "contain",
  "slot": 7,
  "slotId": "slot-3",
  "offsetMs": 2000,
  "slotStartMs": 1795506410000,
  "nextChangeAt": "2026-11-24T09:00:10.000Z",
  "transitionMs": 400,
  "opacity": 1,
  "placeholder": false,
  "warnings": []
}
```

The values above are illustrative; the exact source/destination rectangles come from the image and display metadata. Fit modes are `contain` (no crop), `cover` (crop to fill), and `stretch` (distortion warning when aspect differs by more than 10%). Canvas mode computes a crop of the image placed on the virtual canvas. Canvas plus 90/270 rotation is deliberately marked `CANVAS_ROTATION_UNVERIFIED`; 0/180 and non-canvas rotations are covered by tests.

## Server API

The server is in [`apps/server/server.js`](apps/server/server.js). It binds to `127.0.0.1` by default and stores state in JSON with atomic replacement.

| Method | Path | Notes |
|---|---|---|
| `GET` | `/api/time` | Server milliseconds, no-store |
| `GET` | `/api/sites` | Site summaries, demo keys, player links |
| `GET` | `/api/sites/:siteId` | Full site/local demo data for preview |
| `GET` | `/api/sites/:siteId/manifest?displayId=...` | Display manifest, no-store |
| `POST` | `/api/displays/register` | `{siteKey|siteId, displayId?, hardwareId, resolution?, orientation?}` |
| `POST` | `/api/displays/:id/heartbeat` | Last-seen and render telemetry |
| `DELETE` | `/api/displays/:id` | PoC-only display removal; row/grid reflows, custom leaves a reusable empty slot |
| `GET` | `/api/demo` | Image sets 0/1/3/10 and scenario presets |
| `POST` | `/api/admin/reset` | PoC-only demo reset |

The manifest is a snapshot: site, group, layout, playlist, images, all group displays, mode, epoch, dwell, validation issues, and the LCM pattern. A display page registers with a site key or display link, fetches its manifest, and computes its own current plan. Heartbeats every 30 seconds update status; the server derives `offline` after 90 seconds without a heartbeat (except a deliberately seeded offline demo display).

Example registration:

```powershell
curl.exe -X POST "http://127.0.0.1:4174/api/displays/register" `
  -H "content-type: application/json" `
  -d "{\"siteKey\":\"demo-a\",\"hardwareId\":\"manual-test-1\",\"resolution\":{\"width\":1920,\"height\":1080}}"
```

Auto registration adds a display to the first group. Single layouts become a two-display row; row/column/grid layouts reflow; a custom layout is accepted only when it has an empty slot. Existing playback epochs are preserved during add/remove. This is a PoC policy, not an admin UX decision.

## Player

- Registers with `?site=...&display=...` or the form using a site key; persists a display link and hardware ID locally.
- Calls `/api/time` 8 times and chooses the minimum-RTT sample; offset is used with `performance.now()` so a local wall-clock change does not jump playback. Resyncs every 30 seconds and after visibility/network recovery.
- Fetches the manifest every 5 seconds, sends heartbeats every 30 seconds, and computes its next change from the engine.
- Full-screen canvas rendering with contain/cover/stretch, portrait/rotation, 300–500ms fade, cached image preload.
- Debug overlay fields include display ID, image index/count, slot, offset, drift, clock offset/RTT/sample count, next change, viewport, network, SW state, and event count.
- `localStorage` caches the manifest and clock offset; a service worker caches the app shell and `/media/`. A reload while offline continues from cached content and shows an offline badge.
- No hardcoded monitor count or display IDs. Different windows can run different display links concurrently.

## Preview

The preview uses the exact engine functions used by players (`createSnapshot`, `buildRenderPlan`, `patternPreview`, validation, and the shared canvas renderer). It supports:

- site selection and actual site layout,
- 1/4/6/8 and arbitrary 1–12 monitor scenarios,
- 0/1/3/10 image scenarios plus site default,
- all four playback modes and contain/cover/stretch,
- play/pause, absolute time scrub, and “now”,
- add/remove monitor while preserving epoch,
- warnings for missing images, aspect mismatch, stretch distortion, offline displays, empty slots, image shortage, and canvas rotation limits,
- the LCM pattern table, and player links with copy buttons.

## Known limitations / not verified

- No admin authentication, upload endpoint, EXIF/dimension extraction, thumbnail pipeline, scheduling, or Korean admin CRUD. The generic admin UI belongs to the separate prototype/next phase.
- The demo uses original SVG assets. The validator also accepts JPEG/PNG/WebP metadata, but there is no upload flow to inspect real files.
- Synchronized modes share one dwell; varied per-item durations are reported and ignored for sync transitions.
- Canvas crop with 90/270 display rotation remains unverified; 0/180 rotations and non-canvas 90/270 geometry are tested.
- Browser offline reload was verified for 17 seconds, not 10 minutes; the 10-minute case is a deterministic engine simulation with 50ppm drift.
- The four-page browser run lasted 65 seconds. A one-hour soak at 200ms target and a real multi-PC wired-LAN run remain to be performed.
- No physical monitor EDID detection, Windows display topology, kiosk auto-start, watchdog, NTP, or power-loss test. The restart was a graceful server restart.
- JSON state is single-process and has no locking or multi-writer guarantee; it is adequate only for this PoC.
- Port 4173 may be occupied; use `--port` to choose another port.
